# Phase 0 検証手順（第1弾: 参加・字幕・負荷）

対象は PLAN.md §5 の Phase 0 検証項目 **1・2・3・8**。項目 4 の要約試作に使うログもこの手順で取れる。
項目 5〜7（チャット、カメラ差し替え、Docs）は第2弾以降。

## 必要なもの
- 自宅 PC（Windows / Linux / macOS。Windows のメモリ計測は PowerShell を使う。Windows 実機では未検証）
- Node.js 22 以上
- Google Chrome（インストール済みのもの。スクリプトは `channel: "chrome"` で起動する）
- ボット専用 Google アカウント（リカバリ用メール・電話番号はメインアカウントと分ける）
- 自分がホストのテスト用 Meet（メインアカウントで作成し、別端末から参加して話す）

## セットアップ
```bash
npm install
npm run login        # 開いた Chrome でボット用アカウントにログインし、ブラウザを閉じる
```
ログイン情報は `.profile/bot/` に保存される（`.gitignore` 済み。共有しないこと）。

`npm run login` は Playwright を使わず、インストール済み Chrome を `--user-data-dir=.profile/bot` で普通に起動する。
Playwright 経由（自動操作モード）の Chrome では Google のログイン画面が
「このブラウザまたはアプリは安全でない可能性があります」と拒否するため（2026-11-22 Windows 実機で確認）。
ログイン用の Chrome を閉じてから `observe` を実行すること（同じプロファイルは同時に開けない）。

## 実行
```bash
# 手動で参加・字幕 ON にする場合（最初はこちらを推奨）
npm run observe -- https://meet.google.com/xxx-xxxx-xxx --minutes 30

# 自動参加・字幕 ON を試す場合（項目 1・2）
npm run observe -- https://meet.google.com/xxx-xxxx-xxx --minutes 30 --auto
```
- ボットの参加リクエストは、メインアカウント側で承認する。
- 字幕が表示されている時にターミナルで **Enter** を押すと、HTML とスクリーンショットを保存する。
  Enter を押せない起動方法の時は `--snap-every 60`（60 秒ごとに自動保存）を付ける。
- Windows / デスクトップ環境では Xvfb は不要。ディスプレイの無い Linux 機では `xvfb-run -a npm run observe -- ...` で実行する。

### 話す内容の例（項目 3・4 用）
- 普通の会話を数分
- 途中で言い直し（「えーと、明日、いや明後日に」）
- 専門用語・固有名詞を含む文
- 2人で交互に話す（話者の切り替わりの記録を取る）

## 解析
```bash
npm run analyze -- logs/<日時>                         # 字幕らしい要素を探す
npm run analyze -- logs/<日時> --path "<pathの一部>"   # 書き換わり方・更新間隔・寿命
```

## 記録シート
実施: 2026-11-22、Windows 11 / Chrome（Program Files (x86)）/ Node 24。
第1回 = 主催者と同名表示のアカウントで手動参加（字幕なし・約4分）、
第2回 = ボット用アカウント（メインとは別アカウント・表示名は同じ）で `--auto`、30 分。

| 項目 | 確認内容 | 結果 | メモ |
|---|---|---|---|
| 1 | ボットアカウントで参加できたか（ログイン画面で弾かれないか） | OK（条件付き） | Playwright 経由の Chrome では Google ログインが拒否される →  `login` を通常起動の Chrome に変更して回避。ログイン後は Playwright 起動の Chrome でも Meet に入室でき、30 分弾かれなかった。ボットには「参加をリクエスト」ではなく「今すぐ参加」が出たため、**承認が必要な会議での流れは未確認** |
| 2 | `--auto` の参加ボタン操作は成功したか（events.jsonl の `auto-join`） | OK | `/今すぐ参加/` に一致してクリック（ページ表示から約 4 秒） |
| 2 | 字幕 ON は成功したか（`auto-captions`）。入室時の字幕の既定状態・言語は何だったか | OK | 既定は **OFF**。操作バーの「字幕と翻訳」(translate_cc) → 「字幕をオンにする」で ON（`method: menu`、入室から約 6 秒）。言語は最初から **日本語**（字幕欄左下の言語表示）。注意: ボットのマイク・カメラは ON のまま入室する（自動で OFF にする処理が必要） |
| 3 | 字幕の要素を特定できたか（path） | OK | `div[role=region][aria-label=字幕]` の下に、話者ブロック `div.nMcdL` が並ぶ。本文は `div.ygicle`（ブロックの 2 つ目の子 div）。クラス名は難読化されているので、`aria-label=字幕` の region を起点に構造でたどるのが安全 |
| 3 | 話者名はどの要素に出るか | OK | 話者ブロックの 1 つ目の子 `div.adE6rb`（アイコン img ＋ `span.NWpY1d` に表示名）。話者が同じ間は**同じブロックの本文が伸び続ける**（今回 7 分半・282 文字まで 1 ブロック）。**話者の切り替わりは未確認**（人間の話者が 1 人だけだった） |
| 3 | 書き換えの種類（追記 / 書き換え / 短縮）の比率 | 追記 29 / 書き換え 81 / 短縮 9 | 「書き換え」のほぼ全部は**最後の文の末尾だけ**（深さ p50=1 / p90=2 / p99=12 / 最大 18 文字。多くは末尾の句読点「。」→「？」の付け替え）。文は「。 」「？ 」のように**句読点＋半角スペース**で区切られ、**最後の文より前は一度も変わらなかった**。ただし最後の文が**丸ごと消える**ことが 3 回あった（直前の更新から 1.0 / 3.1 / 5.5 秒後） |
| 3 | 更新間隔 p90 / p99（確定待ち時間の目安） | p50 0.34s / p90 10.5s / p99 41.7s | p90 以上は発話の切れ目（無言の時間）なので確定待ちの目安にならない。文の途中の更新はほぼ 0.3〜0.4 秒間隔。**確定待ちは最後の文の消去が 5.5 秒後にも起きたため、2 秒では足りず 6〜8 秒が目安**（下の「確定ロジック案」参照） |
| 3 | 発話してから字幕が出るまでの遅れ（体感・動画で計測） | 未計測 | 次回、話しながら画面を見て体感を記録する |
| 8 | 1〜2 時間後の Chrome 合計 RSS、増え続けていないか | 30 分は横ばい | Windows はプライベートバイト合計で計測（WorkingSet 合計は共有 DLL の重複で約 4 倍の 3.4 GB になる）。入室直後 786 MB → 字幕表示中 920〜945 MB → 無音時 880〜895 MB で安定。JS ヒープ 59〜66 MB、Chrome プロセス 10 個。**1〜2 時間の計測は未実施** |

### 確定ロジック案（PLAN.md §4.2 の更新候補、第2回の結果から）
1. 字幕 region の各話者ブロックについて、本文を「句読点（。？！）＋空白」で文に分ける。
2. **最後の文より前の文は、次の文が始まった時点で確定**（今回、最後の文より前が変わったことは一度もなかった）。
3. 最後の文は、**更新が約 6〜8 秒無ければ確定**。それまでは暫定表示にする（丸ごと消えることがあるため）。
4. 話者ブロックが変わった時は、前のブロックの最後の文も確定する（未確認。話者切り替えの記録が必要）。
5. 同じ話者のブロックは伸び続けるので、文ごとに「確定済みの文字数」を覚えて差分だけ処理する。

### 未確認（次回の検証で確認すること）
- 2 人以上が交互に話した時のブロックの分かれ方（話者の切り替わり）
- 承認が必要な会議での「参加をリクエスト」→承認の流れ
- 発話から字幕表示までの遅れ
- 1〜2 時間連続で動かした時のメモリ
- 1 つのブロックが長くなった時に、古い部分が消えるかどうか（今回は 282 文字まで消えなかった）

## 結果の共有
