# Meeting Partner 企画書（v0.4）

最終更新: 2026-11-23（Phase 0 第1弾の実機結果を反映）

## 0. 決定事項
| 項目 | 決定 |
|---|---|
| 利用者 | 自分用（社外配布しない。自分がホストの会議でのみ使用） |
| Bot 基盤 | 自作（Playwright でブラウザ操作） |
| 実行環境 | 自宅 PC（または自宅 LAN 内の Linux 機）を第一候補。**Windows 11 実機で動作確認済み**（画面ありの PC では Xvfb 不要） |
| 文字起こし | Meet 字幕の DOM 読み取りを第一案、音声 STT を予備案 |
| 資料の出力先 | Google ドキュメント（**会議終了時に一括生成**＋手動ボタンで随時生成） |
| 会議中の表示 | ローカル Web 画面でリアルタイム表示 |
| アバター | 2D |
| 実装言語 | TypeScript（Node.js） |

## 1. コンセプト
自分の Google Meet に「参加者」として入り、会話を聞きながら
1. リアルタイム要約
2. 資料化（議事録・決定事項・ToDo）
3. チャットでの会話参加

を行う AI 会議パートナー。最終形では **2D アバター（映像＋音声）** として発言する。

## 2. 技術的前提（調査結果）

| 項目 | 状況 | 根拠 |
|---|---|---|
| Meet Media API（公式のリアルタイム音声/映像取得） | 2027-01-15 にエンドポイント停止予定（2026-10-28 告知、新規申込終了） | Google Meet REST API release notes（検索結果経由。本文は本環境から直接取得できず） |
| Meet REST API / Add-ons SDK | GA・継続。ただし会議中チャットへの投稿メソッドは見当たらない | Meet API v2 リファレンス（検索結果） |
| 自作ブラウザボット | 実例あり。headless 検知、UI 変更、ログイン失効・CAPTCHA が保守課題 | 各 OSS / ブログ（検索結果） |
| Meet 字幕の日本語対応 | 対応 | Meet ヘルプ、Workspace Updates 2022-12 |
| 自作ボットでの参加・字幕取得 | **実機で確認済み**（2026-11-22〜23、Windows 11） | [phase0.md](phase0.md) の記録シート |
| 無料アカウントの会議時間 | 3 人以上の会議は 60 分で終了。**ボットも 1 人に数えられる**ため、2 人の会議でも 60 分で切れる（実機で 66 分時点に終了を確認） | Phase 0 第3回 |

**結論:** 公式 API では要件を満たせないため、自作ブラウザボットで実現する。

## 3. アーキテクチャ

```
[自宅 PC（Windows / Linux）]
 ├─ Chrome（headed。画面の無い Linux では Xvfb 上） ← Playwright で操作。ボット専用アカウントのログイン済みプロファイル
 │    ├─ 字幕 DOM 監視 → 確定処理（§4.2）
 │    ├─ 音声 → PulseAudio 仮想デバイス → VAD / 予備 STT（Phase 3 で必須）
 │    ├─ チャット欄: 読み取り / 投稿（DOM 操作）
 │    └─ カメラ/マイク: getUserMedia 差し替え → canvas の 2D アバター＋TTS 音声（Phase 3）
 ├─ Core（Node.js / TypeScript）
 │    ├─ 確定発話ログ（話者・時刻・本文）※ボット自身の発話は除外
 │    ├─ 要約ループ（約1分ごと, 軽量モデル）
 │    ├─ 長時間対策: 約30分ごとに古い生ログを区間要約へ圧縮
 │    ├─ 呼びかけ検知 → 返答生成 → チャット投稿
 │    └─ 議事録清書（上位モデル）→ Google Docs 生成（終了時 / 手動）
 └─ ローカル Web 画面（要約・決定事項・ToDo のリアルタイム表示、Docs 出力ボタン、ボット停止）
```

## 4. 設計詳細

### 4.1 Meet への参加
- ボット専用 Google アカウントを作成。**リカバリ用メール・電話番号はメインアカウントと分離**し、停止時の波及を防ぐ。
- headless はボット検知で弾かれる報告があるため、通常の Chrome を画面ありで使う（画面の無い Linux では Xvfb 上）。
- **ログインは Playwright を使わず、通常起動の Chrome で行う**。Playwright 経由（自動操作モード）の Chrome では、Google のログイン画面が「このブラウザまたはアプリは安全でない可能性があります」と拒否する。ログイン済みのプロファイルを Playwright で開けば、Meet への入室は弾かれなかった（Phase 0 で確認）。
- Chrome はサンドボックス有効で起動する（Playwright 既定の `--no-sandbox` を外す）。
- 入室の自動操作（Phase 0 で実機確認済み）:
  1. 操作の邪魔になるダイアログ（「Meet からデスクトップ通知を受け取る」）を「後で」で閉じる
  2. マイク・カメラを OFF（ボタンは `aria-label="マイクをオフ"` ＋ `data-is-muted` 属性で状態を判定。トグルのショートカットは使わない）
  3. 「参加をリクエスト」（アクセス「制限付き」の会議）または「今すぐ参加」を押す。参加リクエストは自分が承認する
  4. 字幕 ON: 入室時の字幕は **OFF**、言語は最初から **日本語** だった。操作バーの「字幕と翻訳」→「字幕をオンにする」
- **会議の終了を検知して自動で止まる**: 「この会議は終了しました」「主催者が会議を終了して全員を退出させました」「ホーム画面に戻ります」の表示、または会議の URL から離れたこと（Phase 0 で確認、3 秒以内に検知）。
- ボット用アカウントの表示名は、参加者と区別できる名前（例:「Meeting Partner」）にする。話者名でボット自身の発話を除外するため（§4.6）。
- 注意: ブラウザ自動操作は Google 利用規約上グレーになり得る。自分の会議に限定して運用する。

### 4.2 字幕の取得と確定処理
- 字幕は発話中に書き換わる前提で設計する。DOM の変化をそのまま記録しない。
- **字幕 DOM の構造（Phase 0 で確認）**: `div[role=region][aria-label=字幕]` の下に、話者ブロックが並ぶ。各ブロックは話者名（アイコン＋表示名）と本文から成る。クラス名は難読化されているため、`aria-label=字幕` の region を起点に構造でたどる。
  - 同じ人が話し続ける間は、同じブロックの本文が伸び続ける。参加者（端末）が替わると新しいブロックになる。
  - region に残るブロックは最大 22 個ほどで、古いものから消える。消えた要素は後で別の発言の入れ物として**使い回される**。
  - 本文は「。 」「？ 」のように**句読点＋半角スペース**で区切られる。
- **字幕の遅れ**: 発話から表示まで 1 秒未満（体感）。文の途中の更新は 0.3〜0.4 秒間隔。
- **確定条件（Phase 0 の実測で決定。旧案の「2 秒更新が無ければ確定」は不採用）**:
  1. 各ブロックの本文を「句読点（。？！）＋空白」で区間に分ける（句読点だけでは分けない。空白の無い「。」の前は書き換わることがある）。
  2. **最後の区間より前は、次の区間が始まった時点で確定**。実測 880 回の書き換えで、最後の区間より前が変わったことは一度もなかった。
  3. 最後の区間は **6〜8 秒更新が無ければ確定**。最後の区間が丸ごと消えることがあり（最大で直前の更新から 5.5 秒後）、2 秒では足りない。
  4. 新しいブロックができても前のブロックは 1〜3 秒更新が続くことがあるので、前のブロックの最後の区間も 3. と同じく扱う。
  5. 要素の参照ではなく、region 内のブロックの並び（話者名＋本文）を毎回読み直して前回と突き合わせる（要素が使い回されるため）。本文の先頭が変わったら別の発言とみなす。
  6. 同じ部屋の複数端末が同じ声を拾うと、同じ文が別ブロックにほぼ同時（0.4 秒差）に出る。時刻が近く本文が同じものは 1 つにまとめる。
- 確定前のテキストはローカル画面の「暫定表示」にだけ使う。最後の区間の確定待ちにより、要約などに使えるのは発話の 6〜8 秒後になる。
- DOM のセレクタは1ファイルに集約。取得が止まったら検知して画面に警告する。
- **合否基準（Phase 0）**: 実際の自分の会議（専門用語を含む）で、字幕ログから作った要約に致命的な誤りがないこと。満たさない場合は STT 予備案（Google Cloud Speech-to-Text v2 / Chirp 2: ja-JP ストリーミングは「Limited」対応、話者分離なし）と比較する。

### 4.3 LLM（Claude API）
| 役割 | 頻度 | モデル（初期案） |
|---|---|---|
| ローリング要約・決定事項/ToDo 抽出 | 約1分ごと | `claude-haiku-5-5` または `claude-sonnet-5-5` |
| 呼びかけへのチャット返答 | 随時 | `claude-sonnet-5-5`（ストリーミング） |
| 最終議事録の清書 | 終了時 / 手動 | `claude-opus-5-5` |

- 最終的なモデルは Phase 0〜1 で実際の会議ログを使い、品質・遅延・費用を測って決める。
- プロンプト構造: 固定の system（指示・会議メタ情報）→ 発話ログを追記。時刻などの可変値は system に入れず、キャッシュが効くようにする。
- 長時間会議対策: 約30分ごとに古い生ログを区間要約に置き換え、入力量の増加を抑える（置き換え時はキャッシュが作り直しになる点は許容）。
- 出力は構造化出力（JSON スキーマ）で「要約 / 決定事項 / ToDo（担当・期限）/ 未解決論点」。
- `stop_reason: "refusal"` を必ずハンドリング。

### 4.4 Google ドキュメント出力
- 会議中の確認はローカル Web 画面で行う。Docs の逐次更新はしない（Docs API は文字位置ベースのため、セクション単位の置換を繰り返す実装は不具合が出やすい）。
- 会議終了時（または手動ボタン）に、清書結果から **新規ドキュメントを1回で生成** する。
- 構成: 全体要約 / 決定事項 / ToDo / 未解決論点 / 全文ログ。

### 4.5 チャット参加（Phase 2）
- 呼び名（例:「パートナー」）がチャットまたは発話に含まれる時だけ返答する。
- チャット欄への入力・送信は DOM 操作。連投防止のレート制限を入れる。
- 追加モード（個別 ON/OFF）: 定期要約の投稿、論点の抜けの指摘。

### 4.6 2D アバターと音声発話（Phase 3）
- カメラ: ページ読み込み前に `getUserMedia` を差し替え、`canvas.captureStream()` を返す。①静止画＋口パク（音量連動）→ ②Live2D 等で表情・まばたき。
- 音声: TTS 音声を Web Audio で差し替えマイクトラックに流す。
- **自己発話ループ防止**: ボット自身の字幕・チャットを話者名で除外する。加えて「ボットが発話中・直後に確定した発話」には反応しない。
- **割り込み制御**: 字幕は表示まで遅れがあるため、ターンテイキングの判断には使わない。PulseAudio から取った会議音声に VAD（発話区間検出）をかけ、人が話している間は発話しない。
- 既知の注意点: 差し替えスクリプトの注入が遅いと効かない。バックグラウンドタブではフレームが止まる可能性がある。

## 6. 主要リスク
- **UI 変更・ボット検知**: Meet の DOM 変更、ログイン失効・CAPTCHA。セレクタ集約と異常検知で早く気付けるようにする。Phase 0 でも、想定していたボタン名・終了画面の文言が実物と違い、実機で直した（ボタン名は表示中のツールチップと aria-label が違う、など）。
- **会議時間の上限**: 無料の個人アカウントでは、ボットを入れると 3 人以上の会議になり **60 分で終了**する。60 分を超える会議で使うには、ホスト側を Google Workspace など時間制限の無いプランにする必要がある（要確認: どのプランなら制限が外れるか）。
- **規約・アカウント**: 自動操作は規約上グレー。ボットアカウントを分離して運用する。
- **字幕精度**: 専門用語の誤変換。Phase 0 の合否基準で判断する。
- **遅延**: 字幕 → LLM → TTS → 映像 の多段パイプライン。
- **費用**: 要約ループのモデル選定を実測で決める。

## 7. 未確認事項（Phase 0 で確認）
Phase 0 第1弾で確認済み: 入室直後の字幕の既定状態（OFF・日本語）、字幕の表示遅延（1 秒未満）。

まだ確認していないもの:
- データセンター IP（VPS）からのログイン・参加が家庭回線より弾かれやすいか（そのため自宅 PC を第一候補にしている）
- 60 分を超える会議でのメモリ・CPU（Workspace など時間制限の無い環境で測る）
- 1 つの字幕ブロックがとても長くなった時に、古い部分が消えるか（282 文字までは消えなかった）
